# Frees Agent 项目架构说明

## 1. 架构目标与设计哲学

`Frees Agent` 的目标不是做成一次性脚本，而是做成一个可以持续维护和拓展的终端 AI Agent 工程。为了实现这个目标，项目遵循以下架构原则：

1. **命令清晰**：每个 CLI 命令对应独立文件，职责单一
2. **模型清晰**：Provider 抽象层统一接口，新模型即插即用
3. **记忆清晰**：分层记忆架构从启发式到向量检索逐步增强
4. **工作区能力清晰**：索引、查询、上下文组装各司其职
5. **扩展点清晰**：工具、Skill、MCP 都有明确的注册机制

---

## 2. 核心分层总览

```
src/
├── cli.js              # 入口：解析 argv → 路由到命令（Facade 模式）
├── commands/           # 命令层（Command 模式）
├── agent/              # Agent 循环 + 工具系统（Reactor + Strategy）
├── model/              # 模型接入（Abstract Factory 模式）
├── workspace/          # 工作区扫描 + 文件操作
├── memory/             # 记忆系统（分层架构）
├── shell/              # Shell 执行框架（安全代理）
├── skills/             # Skill 系统（插件式）
├── plugins/            # 插件系统（钩子机制）
├── tools/              # 独立工具模块
├── gui/                # Web GUI 模式
├── ui/                 # 展示层
├── utils/              # 工具层（零外部依赖）
└── system/             # 系统能力
```

每一层只依赖其下方的层，不存在循环依赖。

## 3. 命令层详解

### 3.1 职责

命令层负责三件事：
- 解析和验证命令行参数
- 调用下层服务（Agent、Model、Memory 等）
- 格式化并输出结果到终端

命令层是一个薄薄的"胶水层"——不做复杂业务逻辑。

### 3.2 文件清单

| 文件 | 命令 | 功能描述 |
|------|------|----------|

| `complete.js` | `frees-agent complete` | 基于工作区上下文的代码补全 |

```
CLI 输入
    │
    ▼
cli.js: argv 解析 → 提取 command + options
    │
    ▼
```

## 4. Agent 循环层详解

Agent 层是 Frees Agent 的核心大脑，管理 AI Agent 的运行循环、工具调用和执行编排。

### 4.1 组件结构

```
src/agent/
├── chat-tool-loop.js      # 聊天模式工具循环（核心）
├── edit-loop.js           # 编辑模式 Agent 循环
├── orchestration.js       # 工具编排（读写分区、并发控制）
├── prompts.js             # 系统提示词 + 工具描述
├── tools.js               # 统一工具箱（别名映射、MCP 集成）
└── reasoning.js           # 规划层与反思层
```

### 4.2 聊天工具循环 (chat-tool-loop.js)

聊天工具循环是 Frees Agent 最核心的运行机制。其工作流程如下：

```
用户消息
    │
    ▼
┌─────────────────────────────────────────┐
│ 1. 构建上下文                              │
│    - 系统提示词（含工具描述）               │
│    - 记忆注入（用户画像 + 向量召回）         │
│    - Skill 注入（匹配的 SKILL.md 内容）      │
│    - 会话历史（裁剪后）                     │
│    - 工作区上下文（相关文件）               │
└──────────────┬──────────────────────────┘
               │
               ▼
┌─────────────────────────────────────────┐
│ 2. 调用模型（流式）                        │
│    - streamChat(messages, options)       │
│    - 实时输出内容片段到终端               │
└──────────────┬──────────────────────────┘
               │
               ▼
┌─────────────────────────────────────────┐
│ 3. 检测工具调用                            │
│    - 解析响应中的 JSON 动作                │
│    - 提取工具名和参数                      │
└──────────────┬──────────────────────────┘
               │
     ┌─────────┴─────────┐
     │                    │
     有工具调用           无工具调用
     │                    │
     ▼                    ▼
┌──────────────┐    ┌──────────────┐
│ 4. 执行工具   │    │ 回复用户      │
│    - 分区执行  │    │    - 保存到   │
│    - 只读并发  │    │      会话历史  │
│    - 写入串行  │    │    - 记忆提取  │
│    - 结果截断  │    │    - 完成     │
└──────┬───────┘    └──────────────┘
       │
       ▼
┌──────────────┐
│ 5. 返回结果   │
│    给模型继续   │
│    (回到步骤2) │
└──────────────┘
```

**关键实现细节**：

- **重试机制**：EAGAIN/ETIMEDOUT/ECONNREFUSED 自动重试（最多 2 次）
- **消息裁剪**：保留首尾各 20 条消息，中间摘要压缩
- **结果截断**：保持结构完整性，content/stdout 优先裁剪
- **中断支持**：通过 AbortSignal 支持 Ctrl+C 中断
- **非法 JSON 保护**：连续 3 次解析失败则强制终止循环

### 4.3 编辑循环 (edit-loop.js)

编辑模式专为代码修改设计，支持多步 Agent 操作：

```
用户请求
    │
    ▼
┌─────────────────────────┐
│ 1. 构建编辑上下文          │
│    - 工作区文件索引         │
│    - 项目结构描述          │
│    - 编辑约束（最大步数）   │
└────────┬────────────────┘
         │
         ▼  (最多 14 步)
┌─────────────────────────┐
│ 2. Agent 决策循环          │
│    - 解析 JSON 动作        │
│    - 执行工具              │
│    - 输出截断（8000 字符） │
│    - 检查终止条件          │
└────────┬────────────────┘
         │
         ▼
┌─────────────────────────┐
│ 3. 输出最终结果            │
│    - 修改的文件列表        │
│    - 变更摘要              │
│    - 错误报告              │
└─────────────────────────┘
```

与聊天循环的关键区别：
- 只处理单个 JSON 对象（不支持并行工具）
- 串行执行所有工具（代码编辑必须有序）
- 默认最大步数为 14 步
- 支持 `dryRun` 模式（规划而不落盘）

### 4.4 工具编排 (orchestration.js)

工具编排层实现了读写分区执行策略：

```
工具调用列表
    │
    ▼
partitionTools()
    │
    ├── 只读工具组：list_files, search_text, read_file, web_fetch
    │   └── 并发执行（默认 5 并发）
    │
    └── 写入工具组：write_file, replace_in_file, bash
        └── 串行执行
```

**并发控制实现**：

```js
export async function executeToolBatch(toolUses, runToolFn, options = {}) {
  const { concurrency = 5 } = options;
  const results = [];
  const semaphore = new Semaphore(concurrency);
  const tasks = toolUses.map(use => semaphore.run(async () => {
    const result = await runToolFn(use.name, use.args);
    results.push({ name: use.name, result });
  }));
  await Promise.all(tasks);
  return formatToolResults(results);
}
```

### 4.7 推理引擎 (reasoning.js)

提供**多步任务分解**和**回答质检**功能。

- 调用专属的 `plannerClient`（可配置独立模型）

- 检查回答的逻辑完整性和可执行性
- 对有问题的回答进行修订

## 5. 模型层详解

### 5.1 架构设计

模型层使用 Abstract Factory 模式，每种 Provider 实现相同的接口：

```
src/model/
├── index.js              # 工厂入口：根据 provider 名创建客户端
├── anthropic.js          # Anthropic API 客户端
├── openai-compatible.js  # OpenAI 兼容 API 客户端（LM Studio、vLLM、OpenAI）
└── ollama.js             # Ollama 本地模型客户端
```

### 5.2 Provider 接口协议

```typescript
interface ModelProvider {
  streamChat(messages: Message[], options?: ChatOptions): AsyncGenerator<string>;
  chat(messages: Message[], options?: ChatOptions): Promise<string>;
  listModels?(): Promise<ModelInfo[]>;
}

interface Message {
  role: 'system' | 'user' | 'assistant';
  content: string;
}

interface ChatOptions {
  maxTokens?: number;
  temperature?: number;
  signal?: AbortSignal;
}
```

### 5.3 Provider 自动回退

```js
async function findAvailableProvider(config) {
  const PROVIDER_PRIORITY = ['ollama', 'openai-compatible', 'mcp', 'anthropic'];
  for (const name of PROVIDER_PRIORITY) {
    const providerConfig = config.providers?.[name];
    if (!providerConfig) continue;
    const client = await createProvider(name, providerConfig);
    if (await pingProvider(client)) return { name, client };
  }
  throw new Error('No available provider found');
}
```

当 `conversation.autoProviderFallback = true` 时，系统会按可用性自动探活并回退 provider。

## 6. 记忆系统架构

### 6.1 分层设计

```
┌───────────────────────────────────────────────┐
│              持久化存储层                       │
│  store.js: 加载/保存/合并/迁移/跨设备同步       │
│  记忆类型: profile / durable-memories / sessions │
└───────────────────┬───────────────────────────┘
                    │
┌───────────────────▼───────────────────────────┐
│                记忆管理层                       │
│  manager.js: 注入/更新/压缩编排                 │
└───────────────────┬───────────────────────────┘
                    │
┌──────────┬────────┴────────┬──────────────────┐
│          │                 │                  │
▼          ▼                 ▼                  ▼
heuristics.js  ingest.js    vector.js         tasks.js
启发式提取     LLM 语义提取   向量索引           任务记忆
纯正则匹配     结构化抽取     FNV-1a 嵌入        状态跟踪
姓名/目标/偏好  配置文件/项目   CJK 感知分词       长期待办
```

### 6.2 各层职责

| 层 | 文件 | 成本 | 频率 | 精度 |
|----|------|------|------|------|
| 启发式提取 | `heuristics.js` | 零（纯正则） | 每次对话 | 低 |
| 语义提取 | `ingest.js` | 高（LLM 调用） | 定期 | 高 |
| 向量索引 | `vector.js` | 中（哈希计算） | 按需召回 | 中 |
| 持久化 | `store.js` | 低（JSON IO） | 关键节点 | 精确 |

### 6.3 关键算法

**去重压缩**：基于词重叠率判断重复（>70% 判定为重复）

```js
function compactSimilarMemories(memories, threshold = 0.7) {
  const result = [];
  for (const mem of memories) {
    const isDuplicate = result.some(existing =>
      wordOverlapRate(mem.content, existing.content) > threshold
    );
    if (!isDuplicate) result.push(mem);
  }
  return result;
}
```

**向量召回**：低阈值（0.06）召回，按余弦相似度排序，top-K 默认 6

**限幅保护**：全局最大 200 条，每类最多 60 条

### 6.4 Token 预算链

```
systemPrompt (含记忆注入)    → 系统提示词
prompt (含工作区+Skill+联网) → 当前用户输入
history (含最近的对话轮次)    → 历史消息
                          ↓
maxRecentContextTokens = 2800 (硬上限: 3200)
```

历史消息裁剪策略：
1. 按 token 倒序从最新消息开始往回取
2. 如果单条消息超过预算，截取其尾部
3. 如果总预算仍超过，按 0.7 比例缩减历史和最大消息数
4. 始终移除开头的 `assistant` 消息

## 7. 工作区层详解

### 7.1 组件职责

| 文件 | 职责 | 关键特性 |
|------|------|----------|
| `indexer.js` | 工作区文件递归扫描 | 24MB 预算保护、gitignore 感知 |
| `queries.js` | 文件读取与内容搜索 | 行号标注、智能字符串匹配 |

### 7.2 智能字符串匹配

当用户在聊天中引用代码时，Frees Agent 使用三层匹配策略：

1. **精确匹配**：直接搜索完整字符串
2. **引号归一化匹配**：将弯引号转为直引号后搜索
3. **邻近行提示**：没有精确匹配时，返回最近似行及其上下文

### 7.3 索引预算保护

```js
const BUDGET_LIMIT = 24 * 1024 * 1024; // 24MB

async function indexWorkspace(rootPath) {
  let budget = BUDGET_LIMIT;
  const files = [];
  for await (const file of walkDirectory(rootPath)) {
    if (file.size > budget) continue;
    files.push(file);
    budget -= file.size;
  }
  return files;
}
```

## 8. MCP 系统架构

### 8.1 连接生命周期

```
McpManager
  ├── getOrConnect(name)
  │   └── McpConnection._connectStdio()
  │       ├── spawn 子进程 (npx @tavily/mcp 等)
  │       ├── 发送 initialize (协议版本 2024-11-05)
  │       ├── 接收 capabilities
  │       └── 进入消息循环 (stdout 逐行读取 JSON-RPC)
  │
  ├── listAllTools()
  │   └── tools/list 请求 → 缓存工具列表
  │
  └── callTool(serverName, toolName, args)
      └── tools/call 请求 → args → 返回结果
```

### 8.2 工具命名空间

MCP 工具通过 `mcp__<serverName>__<toolName>` 的三段式命名空间注入到工具箱中。

### 8.3 连接管理特性

- **超时控制**：单次 MCP 请求默认 30 秒超时
- **缓存管理**：每次 `callTool` 后自动清除工具列表缓存
- **自动重连**：`getOrConnect` 检测连接状态，自动重连已断开的连接
- **优雅关闭**：`disconnectAll` 清理所有待处理的 Promise

## 9. Shell 执行安全体系

`src/shell/shell-exec.js` 提供安全的 shell 命令执行：

### 9.1 危险命令拦截

```js
const DANGEROUS_PATTERNS = [
  /\|.*curl\s/,
  /\|.*wget\s/,
  /\|.*nc\s/,
  />\s*\/dev\/(tcp|udp)\//,
  /:\s{0,10};\s{0,10}/,
  /rm\s+-rf\s+(\/|\/~)/,
  /chmod\s+-R\s+0{4}\s+/,
  /mkfs\.\w+|dd\s+if=\/dev\/zero/,
];
```

### 9.2 执行控制

- **超时控制**：默认 30 秒，可通过 `timeoutMs` 参数调整
- **输出截断**：1MB 最大捕获量，防止内存溢出
- **AbortSignal 支持**：兼容 AbortController 取消机制
- **自动 shell 检测**：bash/zsh/cmd/powershell

## 10. 插件系统架构

### 10.1 插件接口

```js
class FreesAgentPlugin {
  // 生命周期回调
  async onToolCall(toolName, args, context);
  async onMessage(userMessage, context);
  async onResponse(response, context);
  // 能力扩展
  async getTools();
  async getSystemPromptExtra();
}
```

### 10.2 注册与执行

```
PluginRegistry
  ├── register(plugin)       → 类型检查后加入列表
  ├── getTools()             → 聚合所有插件的工具
  ├── getSystemPromptExtra() → 聚合所有插件的提示词扩展
  ├── runOnMessage()         → 顺序执行所有插件（捕获异常）
  └── runOnResponse()        → 顺序执行所有插件（捕获异常）
```

每个插件运行在自己的 try/catch 中，单个插件失败不会影响其他插件。

## 12. 设计模式总结

| 模式 | 使用位置 | 说明 |
|------|----------|------|
| **Facade** | `cli.js` | 统一入口，隐藏内部复杂性 |
| **Command** | `commands/` | 每个命令封装为独立对象 |
| **Abstract Factory** | `model/index.js` | 根据配置创建不同的 Provider 客户端 |
| **Strategy** | `agent/` | 聊天循环和编辑循环是可互换的策略 |
| **Mediator** | `chat.js` | 协调模型、记忆、工具、工作区之间的通信 |
| **Reactor** | `agent/chat-tool-loop.js` | 事件驱动的工具调用循环 |
| **Chain of Responsibility** | Provider 回退 | 按优先级依次尝试 Provider |
| **Proxy** | `shell/shell-exec.js` | 安全代理控制 shell 执行 |
| **Plugin** | `tools.js` (MCP) | 运行时动态加载外部工具 |
| **Pipeline** | `memory/ingest.js` | 多阶段文本处理管线 |
