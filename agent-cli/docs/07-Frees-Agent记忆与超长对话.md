# Frees Agent 的记忆系统与超长对话

> 一个没有记忆的 AI Agent，就像一个有严重失忆症的助手——每次都像第一次见面，记不住你的偏好、项目和进度。Frees Agent 设计了分层记忆系统和超长对话压缩机制，让 Agent 真正具备"记住"的能力。本文详细讲解记忆架构、实现原理和最佳实践。

---

## 第一章：为什么记忆对 Agent 如此重要

### 1.1 没有记忆时，Agent 有多糟糕

想象你每天和同一个 AI 助手工作，但每次对话它都像第一次见到你：

```text
第一天：
你：我叫张三，我的项目是用 React + FastAPI 做的电商平台
助手：好的，明白了！

第二天：
你：帮我改一下登录页面的样式
助手：登录页面？什么项目？什么技术栈？
你：（又要重新介绍一遍...）

一周后：
你：继续优化首页性能
助手：首页？我们之前聊过吗？
```

这就是没有记忆的 Agent。它的问题包括：

```text
1. 每次都从零开始
   ├── 每次对话都要重新交代背景信息
   └── 重复劳动，效率极低

2. 上下文容量有限
   ├── 聊得越长，前面的信息就"挤"没了
   └── 超长对话中，模型开始"忘记"早期信息

3. 无法积累经验
   ├── Agent 不会从过去的工作中学习
   └── 每次都是"新手"状态

4. 不能持续任务
   ├── 今天的进度明天就丢了
   └── 大型项目需要分多次完成，每次都要重新恢复上下文
```

### 1.2 记忆系统的价值

一个完善的记忆系统能带来以下提升：

```text
跨会话一致性
  无论开多少次新对话，Agent 都记得你和你的项目

超长对话稳定性
  即使聊了几百轮，Agent 仍然记得关键信息

个性化体验
  知道你的技术栈偏好、代码风格、工作习惯

积累进步
  随着使用时间增长，Agent 越来越了解你的项目
```

## 第二章：三层记忆架构

Frees Agent 的记忆系统采用分层设计，将不同类型的记忆存储在不同的层级：

```text
┌──────────────────────────────────────────────────────┐
│               Frees Agent 记忆系统                     │
├──────────────────────────────────────────────────────┤
│                                                        │
│  第一层：用户画像（Profile）                             │
│  ┌────────────────────────────────────────────────┐   │
│  │ • 长期稳定，几乎不变的信息                       │   │
│  │ • 用户身份、角色、技术栈、语言偏好               │   │
│  │ • 手动更新，由用户明确告诉 Agent               │   │
│  │ • 跨所有会话共享                               │   │
│  └────────────────────────────────────────────────┘   │
│                                                        │
│  第二层：长期记忆（Durable Memory）                     │
│  ┌────────────────────────────────────────────────┐   │
│  │ • 中长期信息，跨会话复用                        │   │
│  │ • 项目背景、约束条件、固定流程                  │   │
│  │ • 自动积累 + 手动管理                          │   │
│  │ • 跨所有会话共享                               │   │
│  └────────────────────────────────────────────────┘   │
│                                                        │
│  第三层：会话摘要（Session Summary）                    │
│  ┌────────────────────────────────────────────────┐   │
│  │ • 短期信息，当前会话内动态维护                  │   │
│  │ • 关键决定、当前进度、未完成事项                │   │
│  │ • 自动生成和管理                              │   │
│  │ • 仅限当前会话                                │   │
│  └────────────────────────────────────────────────┘   │
│                                                        │
└──────────────────────────────────────────────────────┘
```

### 2.1 第一层：用户画像（Profile）

用户画像存储的是几乎不会变化的用户核心信息：

**存储的内容**：

```json
{
  "profile": {
    "user": {
      "name": "用户张三",
      "role": "全栈开发者",
      "techStack": ["React", "Node.js", "Python", "PostgreSQL"],
      "preferredLanguage": "zh-CN",
      "codeStyle": "prefer functional programming, 4 spaces indent",
      "longTermGoals": [
        "完成电商平台 v2 重构",
        "引入微服务架构"
      ],
      "commonWorkflows": [
        "TDD 开发模式",
        "先写测试再写实现",
        "每次提交前做 code review"
      ]
    }
  }
}
```

**用户画像的特点**：

```text
稳定性：极高。这些信息几乎不会在会话中自动改变。
更新方式：主要由用户通过命令手动更新。
    /profile set name "用户张三"
    /profile set techStack React,Node.js,Python

生命周期：永久保存，直到用户主动修改或清除。
共享范围：所有会话共享。
```

### 2.2 第二层：长期记忆（Durable Memory）

长期记忆存储的是需要跨会话保持的关键信息，但这些信息比用户画像更动态：

**存储的内容**：

```json
{
  "durable_memory": [
    {
      "id": "mem-001",
      "content": "电商平台项目 app 目录结构: src/client (React), src/server (FastAPI)",
      "type": "project_structure",
      "created": "2025-01-15T10:30:00Z",
      "updated": "2025-01-15T10:30:00Z"
    },
    {
      "id": "mem-002",
      "content": "数据库使用 PostgreSQL，ORM 用 SQLAlchemy",
      "type": "tech_decision",
      "created": "2025-01-15T11:00:00Z",
      "updated": "2025-01-15T11:00:00Z"
    },
    {
      "id": "mem-003",
      "content": "认证方案：JWT + refresh token，access token 15 分钟过期",
      "type": "architecture_decision",
      "created": "2025-01-16T09:00:00Z",
      "updated": "2025-01-16T09:30:00Z"
    }
  ]
}
```

**长期记忆的特点**：

```text
稳定性：中等。会随着项目进展不断积累和更新。
更新方式：
  ├── 自动：Agent 在对话中判断哪些信息值得长期记住
  └── 手动：用户通过命令管理
      /memory add "数据库连接字符串在 .env 文件中"
      /memory remove mem-002

生命周期：持续保存，直到用户清除。
共享范围：所有会话共享。
```

### 2.3 第三层：会话摘要（Session Summary）

会话摘要解决的是"对话太长，模型上下文放不下"的问题。当消息列增长超过预设阈值时，较早的消息会被压缩为摘要：

**生成的摘要示例**：

```json
{
  "session_summary": {
    "sessionId": "session-abc-123",
    "startTime": "2025-01-20T14:00:00Z",
    "lastActivity": "2025-01-20T16:30:00Z",
    "messageCount": 157,
    "summary": "本次会话主要完成了电商平台的用户认证模块重构。\n\n- 将 JWT 认证从同步实现改为异步 (commit: a1b2c3d)\n- 新增 refresh token 轮换机制\n- 修复了 token 过期后未正确清除 cookies 的 bug\n- 讨论了下一步的权限系统设计方案，决定使用 RBAC + 资源级权限\n\n未完成事项：\n- 权限系统的数据库模型设计\n- 中间件集成测试\n\n关键决定：\n- 权限模型使用 Casbin 库\n- 权限数据缓存在 Redis 中\n- API 路由权限注解使用 @require_permission decorator",
    "keyDecisions": [
      "使用 Casbin 作为权限管理库",
      "权限数据缓存到 Redis",
      "API 权限用 @require_permission 装饰器"
    ],
    "currentProgress": "认证模块重构完成，进入权限系统设计阶段",
    "openTodos": [
      "权限数据库模型设计",
      "中间件集成测试编写",
      "权限数据种子脚本"
    ]
  }
}
```

**会话摘要的工作流程**：

```text
对话开始
    │
    ▼
消息不断增加...
    │
    ├── 消息数 < N（如 50 条）
    │   └── 完整上下文全部保留
    │
    ├── 消息数 > N
    │   ├── 将最早的一部分消息压缩为摘要
    │   └── 保留最近 M 条原始消息
    │
    └── 持续对话...
        ├── 多次压缩后，摘要会迭代更新
        └── 保留：关键决定 + 进度 + 待办 + 最新消息
```

**会话摘要的压缩策略**：

```text
首次压缩（消息数达到阈值）：
  └── 将最早 N/2 条消息压缩为摘要
  └── 保留最近 N/2 条原始消息

再次压缩（消息数再次达到阈值）：
  └── 保留旧的摘要
  └── 将旧的摘要与中间消息一起压缩为新摘要
  └── 保留最近 N/2 条原始消息

注意：压缩不是截断
  └── 摘要保留了关键决定、进度、目标
  └── 只是去掉了非关键的闲聊和确认信息
```

## 第三章：运行时上下文构建

### 3.1 每次生成前的上下文组合

当用户发送一条消息时，Frees Agent 会在生成回复之前构建完整的上下文：

```text
系统提示词
    │
    ├── 用户画像
    │   └── "你的用户是张三，全栈开发者，技术栈..."
    │
    ├── 长期记忆
    │   └── "以下是用户长期记忆中保存的信息：..."
    │
    ├── 会话摘要（如果有）
    │   └── "当前会话进度：认证模块重构完成..."
    │
    ├── 最近消息（保留最新的 N 条）
    │   └── 用户：帮我设计权限系统的数据库模型
    │   └── 助手：好的，我们先看一下现有的用户表结构...
    │
    └── 当前消息
        └── 用户：好的，就按这个方案来
```

### 3.2 发送给 LLM 的最终提示词结构

```text
<system>
你是 Frees Agent，一个智能编程助手。

[用户画像]
以下是关于当前用户的信息：
- 用户：张三
- 角色：全栈开发者
- 技术栈：React, Node.js, Python, PostgreSQL
- 代码风格：偏好函数式编程，4 空格缩进

[长期记忆]
- 项目是电商平台，前端 React，后端 FastAPI
- 数据库 PostgreSQL + SQLAlchemy
- 认证使用 JWT + refresh token

[会话进度]
- 已完成：认证模块重构
- 进行中：权限系统设计
- 待办：数据库模型、中间件测试、种子脚本
</system>

[最近的对话]
用户：帮我设计权限系统的数据库模型
助手：好的，我们先看一下现有的用户表结构...

用户：好的，就按这个方案来
```

### 3.3 上下文构建的优势

```text
1. 跨会话连续性
   ├── Agent 知道你是谁、用什么技术栈
   └── 不需要每次重新介绍

2. 会话内稳定性
   ├── 即使聊了 500 轮，关键信息仍有摘要
   └── 不会因上下文过长而丢失早期重要决定

3. 项目级理解
   ├── 长期记忆积累了项目知识
   └── 从"什么都不知道"到"越来越懂你的项目"

4. 有序的信息架构
   ├── 画像 → 不变的你
   ├── 长期记忆 → 项目知识
   ├── 摘要 → 当前会话进度
   └── 最近消息 → 具体上下文
```

## 第四章：存储实现

### 4.1 存储路径

```text
默认存储位置：项目目录下的 .frees-agent/data/

.frees-agent/
├── config.json              # 主配置
└── data/
    ├── memory/
    │   ├── profile.json     # 用户画像
    │   └── durable.json     # 长期记忆
    └── sessions/
        ├── session-001.json  # 会话 1
        ├── session-002.json  # 会话 2
        └── ...               # 更多会话
```

### 4.2 数据持久化策略

```text
写入时机：
  ├── 每次用户发送消息后自动保存上下文
  ├── Agent 生成回复后更新摘要
  ├── 用户通过 /memory 命令显式保存
  └── 会话结束时做最后的摘要更新

数据格式：
  ├── JSON 格式，可读性强
  ├── 按会话分文件存储，便于管理
  └── 使用 UTF-8 编码

存储安全：
  ├── 数据存储在本地项目目录内
  ├── 不上传到任何云端服务
  └── 不写入系统全局目录
```

### 4.3 存储配置

你可以在配置文件中控制记忆系统的行为：

```json
{
  "memory": {
    "maxMessagesBeforeSummary": 50,
    "keepRecentMessages": 20,
    "autoSaveInterval": 5,
    "maxDurableMemoryItems": 100
  }
}
```

| 配置项 | 默认值 | 说明 |
|--------|-------|------|
| maxMessagesBeforeSummary | 50 | 超过多少条消息开始压缩 |
| keepRecentMessages | 20 | 压缩后保留的最近消息数 |
| autoSaveInterval | 5 | 每多少条消息自动保存一次 |
| maxDurableMemoryItems | 100 | 长期记忆的最大条目数 |

## 第六章：超长对话的处理策略

### 6.1 核心挑战

```text
LLM 的上下文窗口是有限的（即使是 128K 窗口的模型）

挑战 1：窗口再大也不是无限的
  50 轮对话可能就消耗了 10K~20K token
  100 轮对话可能消耗 30K~50K token
  500 轮对话...窗口再大也不够

挑战 2：信息利用率随长度下降
  研究（"Lost in the Middle"）表明：
  LLM 对上下文中间部分的信息利用率明显低于开头和结尾

挑战 3：成本随长度线性增长
  更长的上下文 = 更高的推理成本（特别是云端 API）
```

### 6.2 Frees Agent 的解决方案

```text
Frees Agent 采用"摘要 + 裁剪"策略，而不是"硬截断"：

硬截断：
  把最早的消息全部扔掉
  → 丢失关键信息

智能摘要：
  把早期消息压缩为结构化摘要
  → 保留关键决定、进度、目标
  → 丢弃非关键细节（语气词、确认信息、重复内容等）
```

### 6.3 摘要的质量控制

为确保摘要不丢失关键信息，Frees Agent 的摘要生成遵循以下原则：

```text
1. 关键信息分类提取
   ├── 技术决策（使用什么库、选择什么方案）
   ├── 任务进度（完成了什么、进行中什么）
   ├── 用户需求和约束（性能要求、兼容性要求）
   └── 待办事项（下一步要做什么）

2. 结构化存储
   └── 摘要使用结构化的 JSON 格式
   └── 便于后续使用时提取特定类型的信息

3. 迭代更新
   └── 前一次的摘要会作为后续摘要的基础
   └── 新信息追加，旧信息保留，不重要的信息被压缩
```

### 6.4 成本优化

```text
处理超长对话时，摘要机制也帮助降低了成本：

1. 减少发送给 LLM 的 token 数量
   ├── 50 轮对话原始 ≈ 15K token
   ├── 摘要后 ≈ 1K token（摘要）+ 5K token（最近 20 条）
   └── 节省了 60% 的 token

2. 避免重复加载
   ├── 每次只加载增量（新增的消息）
   └── 不需要每次都重新加载全部历史

3. 智能分层
   ├── 高频使用的信息（最近消息）→ 完整保留
   ├── 低频使用的信息（摘要）→ 压缩存储
   └── 几乎不用的信息（超早期消息）→ 高度压缩
```

## 第七章：设计决策与工程权衡

### 7.1 为什么使用分层结构而非统一存储

```text
选择分层的理由：

1. 生命周期不同
   ├── 画像：几个月到几年
   ├── 长期记忆：几天到几周
   └── 摘要：几个小时内
   统一存储会混淆不同粒度的信息

2. 更新频率不同
   ├── 画像：几乎不变
   ├── 长期记忆：低频变化
   └── 摘要：每次对话都可能变化
   统一存储导致频繁的写入冲突

3. 访问模式不同
   ├── 画像：每次对话都加载
   ├── 长期记忆：每次对话都加载
   └── 摘要：仅当前会话加载
   分层存储优化了访问效率
```

### 7.2 为什么选择本地存储而非云端

```text
Frees Agent 默认将记忆数据存储在本地，这是一个有意识的设计决策：

本地存储的优势：
  1. 隐私安全 ─── 数据不离开用户机器
  2. 离线可用 ─── 不需要网络连接就能读取记忆
  3. 速度 ─── 本地文件读取，毫秒级响应
  4. 简单可靠 ─── 不依赖外部服务，没有停机风险

本地存储的局限：
  1. 无法跨机器共享 ─── 换了电脑就看不到旧的记忆
  2. 没有备份机制 ─── 需要用户自己备份 .frees-agent 目录
  3. 大文件管理 ─── 长期使用后文件会增多

未来可能的改进方向：
  ├── 支持配置远程存储（S3、数据库等）
  ├── 记忆导出/导入功能
  └── 选择性同步到云端
```

### 7.3 摘要 vs 检索——选择的原因

```text
为什么使用摘要而非向量检索？

摘要方案的优势：
  ├── 确定性：每次生成的摘要内容确定，不会漏掉重要信息
  ├── 结构化：可以明确区分不同类型的记忆
  ├── 低延迟：不需要嵌入计算和向量搜索
  └── 适合对话场景：对话的关键是进展和决定，而非"相似片段"

检索方案的适用场景（RAG）：
  ├── 知识库问答：需要从大量文档中找到相关信息
  ├── 事实查询：需要精确匹配某个具体信息
  └── 开放域问答：需要广泛搜索

结论：
  对话历史和项目知识 → 摘要方案更优
  外部知识库和文档 → 检索方案（RAG）更优
  两者互补，不是互斥关系
```

## 第八章：最佳实践

### 8.1 如何用好记忆系统

```text
1. 初始设置
   第一次使用前，花 2 分钟设置用户画像：
   /profile set name "你的名字"
   /profile set techStack "你的技术栈"
   /profile set goals "你的项目目标"
   → 让 Agent 从一开始就了解你

2. 日常使用中积累长期记忆
   当 Agent 做出了好的方案或发现了重要信息：
   /memory add "重要信息描述"
   → 让 Agent 记住项目中的关键决策

3. 定期维护
   过时的长期记忆会干扰 Agent 的判断：
   /memory remove "过时的信息"
   /memory clear --session-only  # 开始新话题时清理会话
   → 保持记忆的准确性和时效性

4. 查看记忆状态
   时不时的 /memory show 可以帮你了解
   Agent 目前知道什么、不知道什么
   → 及时发现记忆中的遗漏或错误
```

### 8.2 避免的陷阱

```text
过度保存
   每条消息、每个决定都保存到长期记忆
   → 长期记忆膨胀，关键信息被淹没
   → 解决方案：只保存真正重要的信息

从不检查
   从来不看 /memory show
   → 记忆可能已经过时或有误
   → 解决方案：每周检查一次记忆状态

忘记清理会话
   同一个会话持续数周
   → 摘要越来越长，失去压缩意义
   → 解决方案：切换话题时开始新会话

混淆画像和长期记忆
   把项目细节放入画像
   → 画像应该只保存用户自身信息
   → 解决方案：项目信息放长期记忆，用户信息放画像
```

### 8.3 适用场景示例

```text
场景一：长期项目开发
  用户：每天和 Agent 一起开发同一个项目
  → 用户画像：保存角色和技术栈
  → 长期记忆：保存项目架构、关键决策、约束条件
  → 会话摘要：追踪当前开发进度和待办事项

场景二：跨项目切换
  用户：上午开发后端，下午写前端
  → 用户画像：保存完整的技能栈
  → 长期记忆：每天清理一次，只保留跨项目通用的信息
  → 不同项目使用不同的会话

场景三：学习和探索
  用户：用 Agent 学习新技术
  → 用户画像：保存学习目标和当前学习内容
  → 长期记忆：保存学到的关键知识点
  → 会话摘要：记录学习进度和练习题
```

## 第九章：总结与展望

### 9.1 当前能力总结

```text
已经实现的：
  ├── 三层记忆架构（画像 + 长期记忆 + 会话摘要）
  ├── 超长对话压缩（智能摘要替代硬截断）
  ├── 跨会话记忆持久化（记住你和你的项目）
  ├── 记忆管理命令（查看、清理、编辑）
  └── 本地数据存储（隐私安全、离线可用）
```

### 9.2 为什么这很重要

```text
一个没有记忆的 Agent，充其量是一个"问答机器"。
一个有记忆的 Agent，才能成为真正的"开发伙伴"。

从"每次重新认识"到"越来越了解你"，
从"记不住前面聊了什么"到"追踪项目进度"，
从"一次性的对话"到"持续性的协作"。

这就是记忆系统带来的本质转变。
```

### 9.3 与整个 Frees Agent 生态的关系

```text
记忆系统不是孤立的，它与其他 Frees Agent 组件深度配合：

记忆 ←→ Agent 工具链
  记忆提供项目背景知识，工具链执行具体操作
  两者结合 = 知道你要什么 + 能动真格去做

记忆 ←→ 模型 Provider
  记忆系统不绑定特定模型
  本地模型和云端 API 共享同一记忆系统

记忆 ←→ 配置系统
  通过配置文件控制记忆行为
  跨 Provider、跨项目保持一致的记忆体验
```
