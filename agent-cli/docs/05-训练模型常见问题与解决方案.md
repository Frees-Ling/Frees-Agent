# 训练模型常见问题与解决方案

> 模型训练是一项复杂的工程实践，即使是经验丰富的团队也会遇到各种问题。本文系统性地整理了 LLM 微调中最常见的六大类问题，每个问题都提供详细的原因分析、诊断方法和具体的解决方案。

---

## 第一章：模型学不会，效果很差

### 1.1 现象描述

训练完成后，模型在目标任务上表现没有提升，甚至比基础模型更差。具体表现为：

- Loss 下降非常缓慢或根本不下降
- 模型输出与训练数据风格差异很大
- 模型似乎"不理解"指令
- 生成的回答质量明显低于预期

### 1.2 原因诊断

#### 原因一：数据量不足

```text
SFT 最少需要多少数据？
  ├── 风格微调：300~500 条高质量数据
  ├── 任务微调：1000~5000 条
  ├── 领域知识注入：5000~50000 条
  └── 低于这些基线，模型可能学不到有效模式

判断方法：
  ├── 训练 loss 在几个 step 后就接近 0？
  └── 如果是，说明数据太少或太单一，模型在"背答案"
```

**解决方案**：
- 增加数据量，至少达到 1000 条
- 使用数据增强（模板生成、模型辅助生成）
- 考虑降低 LoRA rank（从 16 降到 8），减少可训练参数量

#### 原因二：数据质量太差

```text
常见数据质量陷阱：
  1. 指令和答案对不上
     "请写一个 Python 函数" → 回答内容却是 Java 代码
     解决方案：人工审核，修正不匹配的样本

  2. 样本格式混乱
     有的用 "user/assistant"，有的用 "human/assistant"
     解决方案：统一格式模板

  3. 答案质量低下
     如明显的逻辑错误或事实错误
     解决方案：用更强的模型重新生成 + 人工审核

  4. 数据重复率过高
     同样的样本出现几十次
     解决方案：去重，确保 Unique 样本占比 > 90%

快速检查方法：
  shuf -n 50 train.jsonl | while read line; do
    echo "$line" | python3 -m json.tool | head -20
    echo "---"
  done
  # 人工看 50 条，如果超过 5 条有问题，数据需要清洗
```

**解决方案**：
- 逐条审核数据，标记和剔除低质量样本
- 重新标注或重新生成
- 引入多人交叉审核机制

#### 原因三：学习率不合适

```text
判断方法：
  ├── 学习率太高：loss 在训练初期剧烈震荡或爆炸
  │   ├── 表现为 NaN loss
  │   └── 解决方案：降低学习率 5~10 倍
  │
  └── 学习率太低：loss 下降极其缓慢
      ├── 50 个 step 后 loss 几乎没变
      └── 解决方案：提高学习率 2~3 倍

推荐的学习率范围：
  ├── 全量微调：1e-6 ~ 5e-6
  ├── LoRA：1e-4 ~ 5e-4（推荐从 2e-4 开始）
  └── QLoRA：1e-4 ~ 3e-4
```

**解决方案**：
- 做学习率搜索实验（LR Finder）：从 1e-5 到 1e-3，每个值跑 50~100 steps，找到 loss 下降最快的区间
- 尝试不同的学习率调度器（Cosine、Linear）

#### 原因四：训练轮数不够

```text
判断方法：
  ├── 训练 loss 仍在明显下降但训练结束了
  └── 解决方案：增加 epoch（但不要超过 5）

经验法则：
  ├── 1000 条数据：3 epoch 通常足够
  ├── 5000 条数据：2~3 epoch
  ├── 10000+ 条数据：1~2 epoch
  └── 如果 3 epoch 后 loss 还在明显下降，需要更多数据而非更多 epoch
```

**解决方案**：
- 增加训练轮数
- 但要注意监控验证集，防止过拟合

#### 原因五：训练目标不清晰

```text
典型场景：
  用户想提高模型的代码能力
  但训练数据中混入了大量通用对话数据
  → 模型不知道该重点学什么

解决方案：
  ├── 明确本次训练的唯一核心目标
  ├── 训练数据聚焦在这个目标上
  └── 不要一次想解决所有问题
```

### 1.3 系统性诊断流程

```text
当发现"模型学不会"时，按以下顺序排查：

Step 1: 检查一条数据能否正常训练
  └── 只拿 1 条数据训练 50 steps
      → Loss 是否稳步下降到接近 0？
          ├── 是 → 数据加载和训练流程正确
          └── 否 → 检查代码、数据格式、模型加载

Step 2: 检查 50 条数据
  └── 用 50 条高质量数据训练 100 steps
      → 模型输出是否开始模仿数据风格？
          ├── 是 → 数据问题，扩大数据量
          └── 否 → 超参数问题，调整学习率

Step 3: 检查数据质量
  └── 随机抽 50 条人工审核
      → 数据质量是否合格（错误率 < 5%）？
          ├── 是 → 扩大数据量到 1000+
          └── 否 → 清洗数据

Step 4: 检查超参数
  └── 梯度流是否正常？（没有消失/爆炸）
      → 调整学习率、梯度裁剪
```

## 第二章：模型过拟合

### 2.1 现象描述

```text
训练集指标：非常好（loss 接近 0）
验证集指标：没有提升甚至变差
输出表现：训练数据中的模式被过度复制
泛化能力：对于没见过的指令表现很差
```

### 2.2 原因与解决方案

#### 原因一：训练轮数过多

```text
这是最常见的过拟合原因

诊断：
  对比训练集 loss 和验证集 loss
  如果训练集 loss 持续下降但验证集 loss 已开始上升 → 过拟合

解决方案：
  ├── 减少 epoch（一般 SFT 不超过 3 epoch）
  ├── 启用早停（Early Stopping）
  └── 增加验证集 size，使指标更稳定
```

#### 原因二：数据量太少且过于单一

```text
诊断：
  训练数据中有大量相似的样本（如 90% 的样本都在问"写代码"）
  → 模型只学会了这一种模式

解决方案：
  ├── 增加数据多样性（至少覆盖 5~10 种指令类型）
  ├── 数据增强（回译、模板扩展）
  └── 加入通用数据（从基础模型的训练数据中采样）
```

#### 原因三：LoRA rank 过高

```text
原理：
  过高的 rank（如 128+）给模型太多可训练参数
  在小数据集上容易过拟合

解决方案：
  ├── 降低 rank（16 → 8 → 4）
  ├── 增加 lora_alpha（降低更新幅度）
  └── 增加 lora_dropout（0.05 ~ 0.1）
```

#### 原因四：学习率过高

```text
原理：
  过高的学习率导致模型参数在训练数据上过度适配

解决方案：
  ├── 降低学习率（减半尝试）
  ├── 使用 weight_decay 正则化
  └── 减少训练步数
```

### 2.3 过拟合的预防措施

```text
1. 数据层面
   ├── 训练集 : 验证集 : 测试集 = 8:1:1
   ├── 确保验证集与训练集分布一致但不重叠
   ├── 数据增强增加多样性
   └── 混入通用数据防止专化

2. 训练层面
   ├── Early Stopping（patience=3~5）
   ├── Weight Decay（0.01~0.1）
   ├── Dropout（0.05~0.1 for LoRA）
   ├── Gradient Clipping（max_norm=1.0）
   └── Label Smoothing（可选）

3. 模型层面
   ├── 使用更低的 LoRA rank
   ├── 只微调部分层（如只微调 attention 层）
   └── 使用更强的正则化
```

## 第三章：灾难性遗忘（Catastrophic Forgetting）

### 3.1 现象描述

```text
训练前：模型能正确回答通用问题（如"什么是递归？"）
训练后：模型在新任务上表现好了，但"什么是递归"也不会回答了！

这是 LLM 微调中最令人头疼的问题之一。
```

### 3.2 原因分析

灾难性遗忘的根本原因是：

```text
微调只在新数据上更新参数
     ↓
新数据的分布 ≠ 原始预训练数据的分布
     ↓
模型参数向新数据方向偏移
     ↓
原本学会的"知识"被覆盖
```

### 3.3 严重程度评估

遗忘程度与以下因素正相关：

```text
遗忘风险 = 训练强度 × 数据偏差 × 参数重叠度

训练强度：
  ├── 学习率越大 → 遗忘越快
  ├── 训练轮数越多 → 遗忘越多
  └── Rank 越高 → 变化幅度越大

数据偏差：
  ├── 新数据与通用数据分布差异越大 → 遗忘越严重
  └── 例如：纯代码微调 → 通用对话能力下降最明显

参数重叠度：
  ├── 不同能力共享相同的模型参数
  └── 微调改变了这些共享参数 → 所有共享能力都受影响
```

### 3.4 解决方案

#### 方案一：混入通用数据（最有效）

在微调数据中混入 10%~50% 的通用指令数据：

```python
# 混合数据策略
finetune_data = load_dataset("json", data_files="domain_specific_data.jsonl")
general_data = load_dataset("json", data_files="general_instruction_data.jsonl")

# 按比例混合：70% 领域数据 + 30% 通用数据
from datasets import concatenate_datasets
mixed_data = concatenate_datasets([
    finetune_data.select(range(int(len(finetune_data) * 0.7))),
    general_data.select(range(int(len(general_data) * 0.3))),
])
mixed_data = mixed_data.shuffle(seed=42)
```

推荐混合比例：

| 场景 | 领域数据 | 通用数据 | 说明 |
|------|---------|---------|------|
| 风格调整 | 30% | 70% | 主要调整风格，保留通用能力 |
| 任务微调 | 50% | 50% | 平衡新任务和旧能力 |
| 领域强注入 | 70% | 30% | 需要大量领域知识，接受一定遗忘 |
| 极端领域 | 90% | 10% | 必须大量领域数据，需单独做通用能力恢复 |

#### 方案二：降低学习率

```text
更小的学习率 → 参数变化幅度更小 → 遗忘风险降低
推荐：
  ├── 全量微调：1e-6（比标准低 2~5 倍）
  └── LoRA：5e-5（比标准低 2~4 倍）
```

#### 方案三：控制微调强度

```text
使用更低的 LoRA rank（r=8→4→2）
只微调部分模块（如只微调 v_proj + o_proj）
减少训练轮数（1 epoch 以内）
```

#### 方案四：使用 DPO 或 PPO

DPO 和 PPO 通过对齐训练（偏好优化），可以在保持通用能力的同时优化特定行为：

```text
RLHF/DPO 的核心优势：
  不是让模型"学新内容"
  而是让模型学会"偏好什么"
  对原有参数结构的改变更小
```

#### 方案五：多任务学习

在微调中同时保持多个任务的数据，让模型在所有任务上都能保持：

```python
# 多任务混合示例
tasks = {
    "code_generation": 30,      # 30% 数据
    "general_chat": 30,         # 30% 数据
    "reasoning": 20,            # 20% 数据
    "knowledge_qa": 20,         # 20% 数据
}
```

### 3.5 遗忘检测流程

```text
训练前：
  1. 在通用能力测试集上评估基础模型 ✓
  2. 在目标任务测试集上评估基础模型 ✓
  3. 记录所有指标作为基线

训练后：
  1. 在通用能力测试集上评估微调模型
  2. 在目标任务测试集上评估微调模型
  3. 对比训练前后的各项指标

判断：
  ├── 目标任务提升 + 通用能力保持 = 成功微调
  ├── 目标任务提升 + 通用能力下降 < 5% = 可接受
  ├── 目标任务提升 + 通用能力下降 > 10% = 需要调整策略
  └── 目标任务变化不大 + 通用能力下降 = 失败的微调
```

## 第四章：显存不够

### 4.1 显存占用分析

```text
训练时的显存消耗主要来自：

模型权重和梯度 ~ 40%
  ├── 模型参数（BF16 7B ≈ 14GB）
  └── 优化器状态（AdamW ≈ 额外 8GB for 7B）

激活值（Activations）~ 40%
  ├── 前向传播时存储的中间结果
  └── 与 batch_size × seq_length 成正比

临时缓冲区和其他 ~ 20%
  └── GradScaler、通信缓冲区等
```

### 4.2 各种情况下的显存需求估算

| 模型 | 精度 | 纯推理 | 全量微调 | LoRA | QLoRA |
|------|------|--------|---------|------|-------|
| 1.5B | BF16 | ~3GB | ~8GB | ~3.5GB | ~2.5GB |
| 3B | BF16 | ~6GB | ~16GB | ~7GB | ~4GB |
| 7B | BF16 | ~14GB | ~56GB | ~16GB | ~6GB |
| 13B | BF16 | ~26GB | ~104GB | ~30GB | ~10GB |
| 34B | BF16 | ~68GB | ~272GB | ~72GB | ~22GB |
| 70B | BF16 | ~140GB | ~520GB | ~148GB | ~48GB |

### 4.3 显存优化策略

按效果从好到差排列：

#### 策略一：使用 QLoRA（最推荐）

```text
效果：显存减少 80%+
方法：将基础模型 4-bit 量化，只训练 LoRA 适配器
代价：训练速度降低 15~30%

配置示例：
  ├── load_in_4bit=True
  ├── bnb_4bit_use_double_quant=True
  ├── bnb_4bit_quant_type="nf4"
  └── bnb_4bit_compute_dtype=torch.bfloat16
```

#### 策略二：减小 Batch Size + 梯度累积

```text
效果：线性减少激活值显存
代价：训练速度降低（通信开销增加）

配置示例：
  ├── per_device_train_batch_size=1
  └── gradient_accumulation_steps=16
  → 等效 batch_size=16，但显存只有 1/16
```

#### 策略三：梯度 Checkpointing

```text
效果：减少 ~50% 激活值显存
代价：训练速度降低 ~20%
代价：需要额外的前向重计算

配置示例：
  ├── model.gradient_checkpointing_enable()
  └── 配合 Unsloth 时使用 use_gradient_checkpointing="unsloth"
```

#### 策略四：混合精度训练

```text
效果：减少 ~40% 显存
代价：几乎无（BF16 精度对收敛影响极小）

配置示例：
  ├── bf16=True（优先，更稳定）
  └── fp16=True（备选，需要注意 loss scaling）
```

#### 策略五：优化器 8-bit

```text
效果：减少优化器状态显存 50%+
代价：几乎无

配置示例：
  ├── optim="adamw_8bit"
  └── 配合 bitsandbytes 库
```

#### 策略六：参数卸载（Offload）

```text
效果：可以使用远超显存容量的模型
代价：训练速度降低 5~10 倍（有 CPU-GPU 传输开销）

配置示例：
  ├── device_map="auto"
  └── DeepSpeed ZeRO-3 Offload
```

### 4.4 显存不足时的排查清单

```text
1. 是否使用了 QLoRA？（最简单有效的优化）
   └── 否 → 切换到 QLoRA

2. Batch Size 是否过大？
   └── 尝试 per_device_train_batch_size=1

3. 是否开启了梯度 Checkpointing？
   └── 否 → 开启

4. 是否使用了混合精度（BF16/FP16）？
   └── 否 → 开启

5. 序列长度是否过长？
   └── 检查 max_seq_length，是否可以用更短的长度

6. 是否使用了 8-bit 优化器？
   └── 否 → 使用 adamw_8bit

7. 是否启用了 Flash Attention 2？
   └── 可额外节省 ~20% 显存

8. 是否可以考虑使用更小的模型？
   └── 7B → 3B 或 1.5B
```

## 第五章：模型输出变乱、答非所问

### 5.1 现象描述

```text
训练完成后，模型输出的典型问题：
  1. 重复输出同一段话
  2. 输出乱码或特殊字符
  3. 输出与用户输入完全无关的内容
  4. 输出格式混乱（Markdown 开始但不结束）
  5. 输出语言混杂（中英文混用）
```

### 5.2 原因与解决方案

#### 原因一：数据风格混乱

```text
表现：
  训练数据中的"助手回复"风格五花八门
  → 模型学不到稳定的输出风格

解决方案：
  ├── 统一所有样本中的助手回复风格
  ├── 建立回复风格指南并严格执行
  └── 删除或重写风格明显异常的样本
```

#### 原因二：指令模板不统一

```text
表现：
  训练数据使用了多种对话模板
  ├── 有的用 <|user|>/<|assistant|>
  ├── 有的用 ### Human:/### Assistant:
  ├── 有的用 [INST]/[/INST]
  └── 甚至有的没有模板，直接拼接

  → 模型在不同模板间混乱

解决方案：
  确保所有样本使用完全相同的对话模板
  使用 tokenizer.apply_chat_template() 统一处理
```

#### 原因三：多轮样本构造质量差

```text
表现：
  多轮对话样本中，模型回复和用户消息混在一起
  或者上下文逻辑断裂
  → 模型学不会在多轮对话中保持连贯

解决方案：
  ├── 确保多轮样本的上下文逻辑连贯
  ├── 每条多轮样本人工审核
  └── 优先使用单轮数据（质量更容易保证）
```

#### 原因四：序列长度设置不当

```text
表现：
  max_seq_length 设置太长，显存不够
  或者训练时截断策略错误，导致关键信息丢失

解决方案：
  ├── 选择合适的 max_seq_length
  ├── 使用正确的截断策略（truncation_side='left'）
  └── 确保训练时的序列长度与推理时一致
```

### 5.3 输出质量修复流程

```text
Step 1: 检查数据格式
  确认所有样本遵循统一格式
  ├── 同样的角色标签
  ├── 同样的模板样式
  └── 同样的助手回复风格

Step 2: 检查推理配置
  调试时使用确定性配置：
  ├── temperature=0.1
  ├── top_p=0.9
  ├── do_sample=True
  └── repetition_penalty=1.05

Step 3: 回退测试
  用基础模型（未微调）生成相同的输入
  → 基础模型输出也乱 → 不是微调的问题，是推理配置问题
  → 基础模型输出正常 → 是微调导致的问题

Step 4: 小批量重训
  缩小到 50 条最高质量的数据重新训练
  → 如果 50 条都能学出稳定风格 → 原始数据中混入了太多噪声
  → 如果 50 条也不行 → 检查超参数和训练代码
```

## 第六章：训练不稳定（Loss 震荡 / 爆炸）

### 6.1 现象描述

```text
Loss 曲线：
  ├── 剧烈震荡（相邻 step 的 loss 差距 > 0.5）
  ├── 突然跳到 NaN
  ├── 先下降后反弹
  └── 完全不下降（维持在初始值附近）
```

### 6.2 原因与解决方案

#### Loss 震荡

```text
可能原因：
  1. 学习率太高 → 降低学习率 2~5 倍
  2. Batch Size 太小 → 增大 batch size 或梯度累积
  3. 数据质量差（包含异常样本）→ 检查并清洗数据
  4. 梯度裁剪未开启 → 设置 max_grad_norm=1.0
```

#### NaN Loss

```text
可能原因：
  1. 学习率过高导致梯度爆炸 → 降低学习率
  2. FP16 的 loss scaling 问题 → 切换为 BF16
  3. 数据中有异常值（无穷大、NaN）→ 检查数据
  4. 模型加载错误（权重损坏）→ 重新下载模型

紧急修复：
  ├── 立即停止训练
  ├── 检查最后几步的 grad_norm
  ├── 降低学习率 10 倍
  ├── 切换到 BF16（如果用的 FP16）
  └── 如果持续 NaN，从上一个可用的 checkpoint 恢复
```

#### Loss 不下降

```text
可能原因：
  1. 学习率太低 → 提高学习率 2~5 倍
  2. 数据为空或全部填充为 padding → 检查数据加载
  3. 模型参数被意外冻结 → 检查 requires_grad 设置
  4. 优化器配置错误（如 weight_decay 过高）→ 检查优化器参数
```

## 第七章：数据相关的常见陷阱

### 7.1 数据泄漏

```text
问题：评测数据出现在训练数据中
后果：评测指标虚高，实际上线后性能远低于预期

检测方法：
  ├── 检查训练集和测试集有没有相同的文本片段
  ├── 使用 MinHash 或 SimHash 做模糊去重
  └── 对训练数据和测试数据做 n-gram 重叠度分析

预防措施：
  ├── 数据切分在数据收集阶段就完成
  ├── 做系统性去重（精确去重 + 模糊去重）
  └── 在公开评测集上做交叉验证
```

### 7.2 数据偏见

```text
问题：训练数据中有系统性偏见
后果：模型继承和放大了数据中的偏见

常见偏见类型：
  ├── 语言偏见（某些语言的数据更多或更少）
  ├── 文化偏见（某些文化视角被过度代表）
  ├── 性别/种族偏见
  └── 知识偏见（某些领域的知识被过度强调）

解决方案：
  ├── 检查数据的分布特征
  ├── 确保数据覆盖多元化的视角
  └── 在评测时加入偏见检测
```

### 7.3 数据格式错误

```text
最常见的问题：
  1. JSON 解析错误（多余的逗号、引号转义错误）
  2. 编码问题（UTF-8 BOM、混合编码）
  3. 截断问题（文本被截断导致不完整）
  4. 特殊字符未转义

预防方案：
  ├── 使用 JSON Schema 验证
  ├── 数据加载后做完整性检查
  └── 每次修改数据后重新跑验证脚本
```

## 第八章：总结——系统性的问题排查框架

### 8.1 先定位问题类型

```text
效果不好 → 是学不会、过拟合还是遗忘？
              ↓               ↓
             数据&超参数问题  数据混合&训练强度问题
                                            
输出混乱 → 是格式、风格还是内容问题？
              ↓               ↓
          格式统一性问题   数据质量问题

训练报错 → 是显存、梯度还是代码问题？
              ↓               ↓
          资源优化         代码检查

效率太慢 → 是数据加载、计算还是通信瓶颈？
              ↓               ↓
          数据预处理优化   并行效率优化
```

### 8.2 万能排查四步法

```text
第一步：验证训练流程是否正确
  └── 用 1 条数据跑 50 step，确认 loss 能正常下降

第二步：验证数据是否可靠
  └── 抽 50 条人工审核，确认数据质量合格

第三步：验证超参数是否合理
  └── 用默认推荐值（LR=2e-4, LoRA r=16, epoch=3）

第四步：验证评测方案是否可靠
  └── 先测基础模型，再测微调模型，确保对比公平
```

### 8.3 一句话

```text
训练中 90% 的问题都可以归结为三类原因：
数据问题、超参数问题、或两者兼有。

先检查数据，再调参数，不要一上来就怀疑代码。
十个训练问题里有八个是数据问题。
```
