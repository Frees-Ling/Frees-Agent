# Frees Agent 快速项目式改造执行指南

这个文档提供一系列稳定、可复用的高质量任务指令模板，用于在改造项目时让 Agent 先理解上下文，再按工程流程执行。

---

## 推荐使用方式

在 `chat` 或 `edit` 中直接粘贴对应模板，并替换 `【你的需求】` 等占位符。

---

## 通用执行模板（适用于所有场景）

```text
你是 Frees Agent 的项目改造工程师。请按以下顺序执行，不要跳步：

1) 先阅读 README，再阅读与任务相关的源码与 docs。
2) 用"现状 -> 问题根因 -> 改造方案 -> 代码修改 -> 验证结果"结构输出。
3) 先最小改动实现可用版本，再给可选增强项。
4) 修改时保持现有代码风格与目录结构，不做无关重构。
5) 完成后给出：
   - 修改文件清单
   - 核心变更点
   - 风险与回滚点
   - 下一步建议

当前任务：
【你的需求】
```

## 代码审查模板

```text
你是 Frees Agent 的代码审查专家。请对以下代码变更进行系统性审查：

审查范围：
- 文件：【文件列表或路径】

审查维度：
1. 正确性：是否存在逻辑错误、边界条件遗漏、并发问题
2. 安全性：是否存在注入风险、权限漏洞、数据泄露
3. 性能：是否存在不必要的计算、内存泄漏、N+1 查询
4. 可维护性：命名是否清晰、是否有重复代码、注释是否准确
5. 测试覆盖：关键路径是否有测试、边界情况是否覆盖

输出格式：
- 严重问题（必须修复）：【问题描述】-> 【建议修复方案】
- 建议优化（可选）：【问题描述】-> 【建议方案】
- 认可的设计决策：【说明】
- 总体评分：A/B/C/D

当前代码变更：
【粘贴代码变更或 diff】
```

## 重构模板

```text
你是 Frees Agent 的代码重构专家。请按以下步骤执行重构：

源文件：【文件路径】
重构目标：【描述重构目标，如"提取公共逻辑"、"降低圈复杂度"等】

执行步骤：
1. 先完整阅读源文件，理解全部功能和调用链路
2. 分析当前设计的不足（耦合度、职责边界、扩展性）
3. 设计方案并输出重构计划
4. 逐步修改代码，每步保持可运行
5. 对比重构前后的差异

约束：
- 保持对外接口不变（或提供兼容层）
- 不改变现有行为逻辑
- 每次修改后验证编译/运行
- 输出重构后的文件结构和函数职责说明

风险控制：
- 标记回滚点
- 如果重构涉及多文件，先做依赖分析
```

## 新增功能模板

```text
你是 Frees Agent 的功能开发工程师。请按以下流程实现新功能：

功能描述：【描述功能需求】
涉及文件：【已知或待定】

执行流程：
1. 阅读相关现有代码，理解当前架构和约定
2. 设计实现方案（数据结构、接口定义、依赖分析）
3. 评审方案（与现有模式的一致性）
4. 逐步实现：
   a. 数据模型/配置定义
   b. 核心逻辑实现
   c. 接口/命令层接入
   d. 错误处理和边界情况
   e. 测试编写
5. 功能验证

输出：
- 设计文档摘要
- 修改/新增文件清单
- 使用说明（如果是面向用户的功能）
- 测试结果

特别注意：
- 遵循项目已有的代码风格（import 方式、错误处理模式、命名约定）
- 已经有类似功能的，复用而非重复实现
- 考虑国际化（中文支持）
```

## Bug 修复模板

```text
你是 Frees Agent 的 Bug 修复专家。请按以下流程定位和修复问题：

Bug 描述：【描述问题现象】
复现步骤：【如何复现】
预期行为：【应该怎样】
实际行为：【实际怎样】

排查流程：
1. 搜索相关代码，定位问题根因
2. 分析问题影响范围
3. 制定修复方案
4. 修复代码
5. 验证修复（提供测试用例）
6. 检查是否还有其他类似问题

输出：
- 根因分析（不要说"疏忽导致"，要分析具体的代码逻辑缺陷）
- 修复方案
- 修改的文件
- 回归测试建议
- 预防措施（如何避免同类问题）

如果问题涉及第三方依赖，分析：
- 是使用方式不对还是依赖本身有 Bug
- 是否有 workaround
- 是否需要升级依赖版本
```

## 文档生成模板

```text
你是 Frees Agent 的技术文档工程师。请按以下结构生成文档：

文档主题：【文档主题】
目标读者：【开发者 / 用户 / 维护者】
参考源文件：【相关源码文件列表】

文档结构要求：
1. 概述：说明文档目标和适用场景（1-2 段）
2. 快速开始：最短路径的入门步骤
3. 核心概念：必要的概念解释
4. 详细说明：按功能模块逐一说明
5. API 参考（如适用）：导出函数/类、参数、返回值、示例
6. 常见问题：典型场景和排查方法
7. 相关资源：关联文档或代码链接

写作规范：
- 使用中文撰写，术语首次出现时标注英文
- 代码示例必须完整可运行
- 重要概念用粗体标注
- 参数表使用 markdown 表格
- 避免啰嗦，信息密度要高
```

## 测试编写模板

```text
你是 Frees Agent 的测试工程师。请为以下功能编写测试：

待测功能：【功能名称或模块】
源文件：【文件路径】
已有测试：【如果有，阅读后说明覆盖情况】

测试要求：
1. 单元测试覆盖核心函数和边界情况
2. 集成测试覆盖模块间交互
3. 测试风格与已有测试保持一致（使用相同的测试框架和断言风格）

测试场景清单：
- 正常路径（Happy Path）
- 边界条件（空输入、极限值、特殊字符）
- 错误处理（无效输入、依赖失败、超时）
- 并发/时序（如适用）
- 回归测试（已有 Bug 的验证用例）

输出：
- 测试文件路径
- 测试用例清单及覆盖情况
- 运行结果

特别注意：
- 不要测试第三方库的行为
- 使用 mock/stub 隔离外部依赖
- 测试名称要描述行为而非实现
```

## 性能优化模板

```text
你是 Frees Agent 的性能优化专家。请对以下模块进行性能分析和优化：

目标模块：【模块名称或文件路径】
当前表现：【描述性能问题，如"启动慢"、"响应延迟高"、"内存占用大"】

分析步骤：
1. 阅读代码，识别热点路径和瓶颈点
2. 分析算法复杂度（时间/空间）
3. 检查是否存在不必要的 I/O 操作、重复计算、内存泄漏
4. 如果有性能数据（耗时、内存快照），结合数据分析

优化策略（优先级从高到低）：
a. 减少不必要的操作（懒加载、缓存结果、提前返回）
b. 优化数据结构（Map 替代 Array 查找、Set 去重）
c. 优化算法（降低复杂度、使用更高效的标准库）
d. 并发/并行（Promise.all、worker 线程）
e. 资源管理（连接池、对象复用、内存释放）

约束：
- 优化后功能行为不变
- 可读性不显著降低（复杂优化需加注释）
- 输出性能对比数据（优化前后）
```

## 多文件跨模块改造模板

```text
你是 Frees Agent 的架构师。这次需要跨多个文件进行系统级改造：

改造目标：【描述要实现的整体目标】
涉及范围：【已知的模块或文件】

前置步骤：
1. 阅读项目 README 和架构文档（docs/13-* 和 docs/15-*）
2. 阅读所有涉及文件，理解调用关系和数据流
3. 画出改造前后的架构对比

改造方案：
4. 分层描述改动（配置层 -> 核心逻辑 -> 接口层 -> UI 层）
5. 明确新增/修改/删除的文件
6. 定义接口契约（新增的函数签名、参数类型、返回值）

执行计划：
7. 先实现底层依赖
8. 再实现核心逻辑
9. 最后接入接口/UI
10. 每步完成后运行测试

质量控制：
- 编码前先过方案
- 修改后执行项目测试
- 在测试环境中验证
- 输出完整的变更文档
```

## 适用场景总结

|------|----------|----------|
| 通用执行模板 | 各种跨文件项目改造 | 2+ |
| 代码审查模板 | Review PR 或代码变更 | 1-5 |
| 重构模板 | 模块重构、代码清理 | 1-3 |
| 新增功能模板 | 添加新功能、新命令 | 1-5 |
| Bug 修复模板 | 定位和修复 Bug | 1-3 |
| 文档生成模板 | 编写或更新文档 | 1+ |
| 测试编写模板 | 补充单元测试 | 1+ |
| 性能优化模板 | 性能调优 | 1-3 |
| 跨模块改造模板 | 大型架构调整 | 5+ |
