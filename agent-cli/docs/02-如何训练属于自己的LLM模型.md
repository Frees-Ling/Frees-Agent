# 如何训练属于自己的 LLM 模型

> 很多开发者都想过"训练一个自己的 LLM"。但这条路有多个层次的难度，需要根据你的目标、资源和团队规模做出务实的决策。本文从工程实践角度，系统性地讲解每种训练路线的技术细节、成本评估和最佳实践。

---

## 第一章：先说实话——四条完全不同的路线

"训练自己的 LLM"这句话，实际上掩盖了四种截然不同的技术路线：

```text
路线一：从零预训练
  ┌──────────────────────────────────┐
  │ 需求：数万亿 token 数据         │
  │ 需求：数千张 GPU                  │
  │ 需求：分布式训练工程团队          │
  │ 预算：数千万 RMB                  │
  │ 典型代表：Llama 3、Qwen2、DeepSeek │
  └──────────────────────────────────┘

路线二：继续预训练（Continual Pretraining）
  ┌──────────────────────────────────┐
  │ 需求：数十亿到数百亿 token 领域数据 │
  │ 需求：数十到数百张 GPU            │
  │ 需求：训练工程经验                │
  │ 预算：数十万到数百万 RMB          │
  │ 典型场景：法律/医疗/金融垂直模型   │
  └──────────────────────────────────┘

路线三：指令微调（SFT / LoRA / DPO）
  ┌──────────────────────────────────┐
  │ 需求：数千到数万条高质量指令数据  │
  │ 需求：1~8 张 GPU（消费级即可）    │
  │ 需求：数据工程和评测能力          │
  │ 预算：数千到数万 RMB              │
  │ 典型场景：企业特定任务调优        │
  └──────────────────────────────────┘

路线四：系统工程增强（RAG / Prompt / Agent）
  ┌──────────────────────────────────┐
  │ 需求：无模型训练，专注系统集成   │
  │ 需求：检索系统 + 提示词工程      │
  │ 需求：API 调用或本地推理          │
  │ 预算：几乎为零（API 费用除外）    │
  │ 典型场景：快速验证和 MVP 阶段     │
  └──────────────────────────────────┘
```

**现实建议**：对于绝大多数个人开发者和中小企业，路线三（指令微调）和路线四（系统工程增强）是最务实的选择。不要因为"训练模型"听起来酷就直接跳到路线一。

---

## 第二章：路线一——从零预训练（Pretraining from Scratch）

### 2.1 技术栈

从零预训练一个 Transformer LLM 涉及以下核心技术：

```text
数据工程
├── 数据采集（CommonCrawl、书籍、论文、代码）
├── 数据清洗（去重、过滤、质量筛选）
├── 数据配比（网络:书籍:代码:多语言 = ?）
├── Tokenization（训练 BPE/SentencePiece 分词器）
└── 数据 Sharding（分布式训练数据切片）

模型架构
├── 架构选择（Dense / MoE）
├── 参数配置（层数、隐层维度、注意力头数）
├── 初始化方法
└── 位置编码 RoPE

训练框架
├── 分布式训练（FSDP / DeepSpeed / Megatron-LM）
├── 学习率调度（Warmup + Cosine Decay）
├── 混合精度训练（BF16 / FP8）
├── 梯度 Checkpointing
├── 通信优化（NCCL 调优）
└── 训练监控（WandB / TensorBoard）

验证与评估
├── Perplexity 监控
├── 下游任务评测（MMLU、HumanEval、GSM8K...）
└── 人工评估
```

### 2.2 典型成本

| 模型规模 | 训练 Token | GPU 需求 | 时间 | 云训练费用（估算） |
|---------|-----------|---------|------|-----------------|
| 7B | 1T | 64×A100 | ~10天 | ~300,000 RMB |
| 13B | 1T | 128×A100 | ~12天 | ~600,000 RMB |
| 70B | 2T | 512×A100 | ~30天 | ~5,000,000 RMB |
| 130B+ | 3T+ | 1024×A100+ | ~60天+ | 数千万 RMB |

### 2.3 谁应该走这条路

- 有充足 GPU 集群预算的大型组织
- 想做底层基础模型的研究机构
- 需要从数据权益角度完全自主可控的场景（如国家级项目）

**绝大多数团队不应该从零预训练**。在开源模型如此丰富的今天，站在巨人肩膀上效率高出几个数量级。

## 第三章：路线二——继续预训练（Continual Pretraining）

### 3.1 技术原理

继续预训练是在已有基础模型上，用领域数据继续做自回归语言建模训练。目标不是从头学习语言，而是在保持通用能力的同时，强化某一垂直领域。

```text
                        继续预训练后
基础模型 ──────────────► 领域增强模型
  通用语料                  通用语料 + 领域语料
                            【显存约为基础模型的 1.5 倍】
```

### 3.2 技术实现

```python
# 典型的继续预训练代码（使用 Hugging Face Transformers）
from transformers import AutoModelForCausalLM, AutoTokenizer, TrainingArguments
from datasets import load_dataset
from trl import SFTTrainer

model = AutoModelForCausalLM.from_pretrained(
    "Qwen/Qwen2.5-7B",
    torch_dtype="bfloat16",
    device_map="auto"
)

tokenizer = AutoTokenizer.from_pretrained("Qwen/Qwen2.5-7B")

# 加载领域数据
dataset = load_dataset("json", data_files="your_domain_data.jsonl")
# 数据格式：每行一个 {"text": "..."}

training_args = TrainingArguments(
    output_dir="./continual-pretrained-model",
    per_device_train_batch_size=2,
    gradient_accumulation_steps=8,
    learning_rate=2e-5,        # 继续预训练的学习率通常较低
    warmup_steps=100,
    num_train_epochs=1,        # 通常只训练 1 epoch
    logging_steps=10,
    save_steps=500,
    fp16=False,
    bf16=True,
    max_grad_norm=1.0,
)

trainer = SFTTrainer(
    model=model,
    args=training_args,
    train_dataset=dataset,
    tokenizer=tokenizer,
    max_seq_length=4096,
)

trainer.train()
```

### 3.3 关键超参数建议

| 参数 | 建议值 | 说明 |
|------|--------|------|
| 学习率 | 1e-5 ~ 5e-5 | 继续预训练的学习率应低于 SFT |
| Warming Steps | 100~500 | 平稳过渡分布差异 |
| 训练 Epoch | 1~3 | 过度训练会导致灾难性遗忘 |
| Batch Size | 尽可能大（取决于显存） | 大 batch 对预训练更友好 |
| 数据混入比例 | 领域数据 30%~70% | 剩余混入通用数据防止遗忘 |

### 3.4 谁应该走这条路

- 需要垂直领域模型（法律、医疗、金融、代码）
- 需要中文能力增强（在英文为主的基础上加入优质中文数据）
- 企业内部知识模型（用内部文档和代码仓库继续训练）

## 第四章：路线三——指令微调（SFT / LoRA / QLoRA / DPO）

### 4.1 这是最实用的路线

对于大多数开发者和团队，指令微调是最具性价比的选择。你只需要：
- 一个基础模型（开源免费）
- 一条到十多条高质量指令数据
- 一张消费级 GPU（甚至 MacBook 也可以做 QLoRA）

### 4.2 四种微调技术的对比

| 技术 | 显存需求 | 训练速度 | 效果 | 适用场景 |
|------|---------|---------|------|---------|
| **全量微调** | ~56GB (7B) | 慢 | 最好 | 有充足 GPU，追求最佳效果 |
| **LoRA** | ~16GB (7B) | 较快 | 接近全量 | 消费级 GPU，平衡效果与效率 |
| **QLoRA** | ~6GB (7B) | 较慢 | 与 LoRA 接近 | 1 张普通显卡甚至 MacBook |
| **DoRA** | ~16GB (7B) | 与 LoRA 相当 | 优于 LoRA | 需要进一步精调质量 |

### 4.3 LoRA 的数学原理

LoRA（Low-Rank Adaptation）的核心思想：对大模型的权重矩阵做低秩分解，只训练分解后的小矩阵。

```text
原始权重（冻结）：W ∈ R^(d×k)
                   ↓
低秩分解：
W' = W + B × A   其中 B ∈ R^(d×r), A ∈ R^(r×k)
                    r << min(d, k)  通常 r = 8, 16, 32, 64
```

训练时，原始权重 W 完全冻结，只更新 B 和 A 两个小矩阵。推理时可以将 B×A 合并回 W（或保持独立加载）。

**LoRA 的关键配置**：

```text
r（秩）：
  ├── r=8：轻量级适配，适合简单风格调整
  ├── r=16：推荐默认值，平衡效果和效率
  ├── r=32：更精细的适配，适合复杂任务
  └── r=64：接近全量微调效果，但显存和计算大幅增加

alpha（缩放因子）：
  ├── 通常设为 r 的 1~2 倍
  └── alpha=16 对应 r=8，alpha=32 对应 r=16

target_modules（目标模块）：
  ├── 通常包括 q_proj, v_proj
  ├── 更好：q_proj, k_proj, v_proj, o_proj
  └── 更完整：加上 gate_proj, up_proj, down_proj

dropout（正则化）：
  ├── lora_dropout=0.05（推荐）
  └── lora_dropout=0.1（数据量较少时）
```

### 4.4 QLoRA 的技术要点

QLoRA = LoRA + 4-bit NormalFloat 量化 + 双重量化 + 分页优化器

```text
基础模型 ──► 4-bit 量化 ──► NF4 计算
  ↑                          │
  │                    LoRA 适配器（BF16）
  │                          │
  训练时只更新 LoRA 参数      │
  基础模型保持量化 + 冻结     │
                              ▼
                         合并/导出
```

QLoRA 的显存节省非常显著：
- 7B 模型：~56GB → ~6GB（全量 BF16 → QLoRA）
- 13B 模型：~104GB → ~10GB
- 70B 模型：~520GB → ~48GB

### 4.5 指令数据的格式和质量

**推荐数据格式（对话式）**：

```json
[
  {
    "conversations": [
      {"role": "system", "content": "你是一个专业 Python 开发助手..."},
      {"role": "user", "content": "帮我写一个 FastAPI 的 JWT 认证中间件"},
      {"role": "assistant", "content": "好的，下面是一个完整的 FastAPI JWT 认证中间件实现..."}
    ]
  }
]
```

**数据质量黄金法则**：

```text
数量不如质量
  500 条精心标注 > 50000 条自动采集

多样性比深挖重要
  覆盖多种指令类型 > 全部集中在某一类

一致性是最容易被忽略的
  同一类问题，回答风格、格式、长度要一致

避免数据泄漏
  训练和评测数据不能有交集
  验证集中不能出现训练数据中的内容
```

### 4.6 完整的 SFT 训练工作流

```text
步骤 1：选择基础模型
  ├── 中文场景：Qwen2.5 / DeepSeek-V2
  ├── 英文场景：Llama 3 / Mistral
  └── 代码场景：Qwen2.5-Coder / DeepSeek-Coder

步骤 2：准备数据
  ├── 数据收集（内部数据、公开数据、合成数据）
  ├── 数据清洗（去重、过滤低质量、格式标准化）
  ├── 数据切分（训练集:验证集:测试集 = 8:1:1）
  └── 格式转换（统一为模型要求的对话格式）

步骤 3：配置训练
  ├── 超参数设置（学习率、batch size、epoch）
  ├── LoRA 配置（r、alpha、target_modules）
  └── 训练策略（warmup、梯度裁剪、学习率调度）

步骤 4：执行训练
  ├── 小规模验证（1 条数据确认流程正确）
  ├── 正式训练（监控 loss、grad norm、学习率）
  └── 定期保存 checkpoint

步骤 5：评测
  ├── 通用能力评测（MMLU、BBH）
  ├── 目标任务评测（自定义测试集）
  ├── 人工抽样评测
  └── 与基础模型的对比测试

步骤 6：导出与部署
  ├── 合并 LoRA 权重（可选）
  ├── 量化（GGUF/GPTQ/AWQ）
  └── 部署到推理服务（Ollama/vLLM/TGI）
```

## 第五章：路线四——系统工程增强（RAG + Prompt + Agent）

### 5.1 不训练也能显著提升模型效果

很多团队陷入一个误区：效果不好就要训练模型。实际上，在不更新模型权重的情况下，通过系统工程可以有惊人的提升：

| 方法 | 效果提升 | 成本 | 实施周期 |
|------|---------|------|---------|
| 提示词工程 | 10%~30% | 极低 | 天级 |
| RAG 检索增强 | 30%~60% | 低 | 周级 |
| Agent 工具链 | 50%~100%+ | 中 | 月级 |
| 三者组合 | 100%~300%+ | 中低 | 月级 |

### 5.2 RAG（检索增强生成）

RAG 的工作流程：

```text
用户提问
    │
    ▼
┌───────────┐    ┌───────────────┐
│ 问题嵌入   │───►│ 向量数据库检索 │
└───────────┘    └───────────────┘
                      │
                      ▼ 返回 Top-K 相关文档
┌───────────┐        │
│ LLM 回答   │◄───────┘
│ (带上下文)  │
└───────────┘
    │
    ▼
最终回答
```

RAG 的核心组件：
1. **文档分块（Chunking）**：将知识文档切分为适当大小的块（通常 256~1024 token）
2. **嵌入模型（Embedding Model）**：将文本转为向量（如 text-embedding-3-small、bge-large-zh）
3. **向量数据库（Vector DB）**：存储和检索向量（如 Chroma、FAISS、Qdrant、Milvus）
4. **检索策略**：相似度搜索、混合搜索（关键词+向量）、重排序（Reranker）

### 5.3 系统性增强路线图

对于个人开发者或小团队，建议的优先级：

```text
第一优先：提示词工程
  ├── 系统提示词优化
  ├── Few-shot 示例
  ├── 思维链提示
  └── 输出格式约束

第二优先：RAG 系统
  ├── 知识库建设
  ├── 检索优化
  └── 上下文增强

第三优先：LoRA / QLoRA 微调
  ├── 风格一致性调整
  ├── 特定格式输出
  └── 领域术语强化

第四优先：继续预训练
  ├── 需要大量领域数据
  └── 需要深度领域知识

第五优先：从零预训练
  └── 有充足资源且必须完全自主
```

## 第六章：训练准备清单

无论选择哪条路线，在开始之前，请确保以下问题都有清晰的答案：

### 6.1 目标与场景

- [ ] 模型将用于什么具体场景？（聊天 / 编程 / 客服 / 写作 / 分析）
- [ ] 对推理速度有什么要求？（实时对话 / 批量处理）
- [ ] 对显存和硬件有什么限制？（云端 / 本地 / 边缘设备）
- [ ] 模型需要支持哪些语言？（中文 / 英文 / 多语言）

### 6.2 数据准备

- [ ] 数据来源是否明确？（内部积累 / 公开数据集 / 合成数据 / 人工标注）
- [ ] 数据质量是否经过验证？（抽样检查 / 一致性测试）
- [ ] 数据量是否足够？（SFT 至少需要数百条高质量样本）
- [ ] 是否包含敏感信息？（需要清洗和脱敏）

### 6.3 评测方案

- [ ] 有哪些客观评测指标？（准确率 / 通过率 / 人工评分）
- [ ] 评测数据集是否准备好？
- [ ] 是否建立了回归评测流程？
- [ ] 是否与基准模型（基础模型或其他同类模型）做了对比？

### 6.4 工程准备

- [ ] 训练框架是否选型完成？（Hugging Face TRL / Axolotl / Unsloth / LLaMA-Factory）
- [ ] 硬件资源是否到位？
- [ ] 训练监控方案是否就绪？（WandB / TensorBoard）
- [ ] 是否有回退方案？（训练失败后如何恢复）

## 第七章：一句话总结

```text
数据 > 算法 > 算力
  高质量数据永远是第一位的。
  好的算法让数据发挥作用。
  足够的算力让前两者变成现实。

从简单开始，逐步深入。
先 RAG，再微调，再预训练。
每一步都做扎实了，再考虑下一步。
```
